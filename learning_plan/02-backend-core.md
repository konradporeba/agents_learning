# Phase 02: Backend core

[← Master plan](README.md) · Previous: [01 Foundations](01-foundations.md) · Next: [03 Realtime chat →](03-realtime-chat.md)

**Estimated effort:** 12–15 hours · **Depends on:** Phase 01

## Outcome

A FastAPI service with authentication, projects and conversations stored in Postgres under Alembic migrations, a MongoDB collection for raw documents, health endpoints, structured logs, a container image, and an integration test suite that runs against real databases in containers.

No AI in this phase. This is the foundation the agent will stand on, and it gives you migrations to practise on in Phase 14.

## Concepts

- **ASGI and async Python**: the event loop, why one blocking call stalls every request, when to use a thread pool.
- **FastAPI**: dependency injection, lifespan events, routers, Pydantic v2 models, generated OpenAPI.
- **SQLAlchemy 2 (async)**: sessions, unit of work, connection pooling, the N+1 problem.
- **Alembic**: autogenerated versus hand-written migrations, upgrade and downgrade, why autogenerate needs review.
- **Authentication and authorisation**: password hashing (argon2), short-lived access tokens and refresh tokens, per-project access checks.
- **Service health**: liveness versus readiness, and why they must not check the same things.
- **Operational basics**: structured JSON logs, request IDs, a consistent error format (RFC 9457 problem details), cursor pagination, idempotency keys.
- **MongoDB**: documents and collections, indexes, when a schemaless store is the right tool.

## Build steps

### Application skeleton

- [ ] App factory, settings object, routers per resource, lifespan that opens and closes pools for Postgres, Redis and MongoDB.
- [ ] Request ID middleware; JSON logs that include the request ID and user ID.
- [ ] One error handler that returns problem-details JSON for every failure.

### Postgres and migrations

- [ ] Models: `users`, `projects`, `project_members`, `conversations`, `messages`, `feedback`.
- [ ] Alembic initial migration. Review the autogenerated file line by line.
- [ ] A second migration that enables the `vector` extension (you need it in Phase 06).
- [ ] A third migration that adds a nullable column to `conversations` (for example `title`), to practise the workflow.
- [ ] A `make migrate` target, and a rule you follow from now on: schema changes only through migrations.

### Auth

- [ ] Register and login endpoints, argon2 hashing, access and refresh tokens.
- [ ] A `current_user` dependency and a `require_project_member` dependency.
- [ ] Every query that touches project data filters by project membership. Write this once in a repository layer, not in every endpoint.

### REST API

- [ ] CRUD for projects and conversations; list messages with cursor pagination.
- [ ] `GET /healthz` (process is alive) and `GET /readyz` (dependencies reachable).

### MongoDB

- [ ] A repository for a `source_documents` collection using PyMongo's async API, with an index on project and source URL.
- [ ] One endpoint that stores a raw document and one that lists them. Ingestion comes in Phase 06.

### Container

- [ ] Multi-stage `Dockerfile`: non-root user, pinned base image, only runtime dependencies in the final stage. Add the `api` service to Compose.

### Tests

- [ ] Unit tests for pure logic (token handling, pagination cursors).
- [ ] Integration tests with Testcontainers for Postgres, Redis and MongoDB, hitting the API through `httpx.AsyncClient`.
- [ ] Authorisation tests: user A cannot read user B's project. Treat these as a permanent regression suite; they matter more once RAG and memory exist.
- [ ] Migration tests: upgrade an empty database to head; downgrade one step and upgrade again.
- [ ] Add the integration job to CI.

## Break it on purpose

- Stop Postgres while the API runs: `/readyz` must fail and `/healthz` must stay green. Explain why that difference matters to Kubernetes.
- Put a `time.sleep(5)` in an async endpoint and send 20 concurrent requests. Measure, then fix it.
- Set the connection pool size to 2 and run 50 concurrent requests. Read the error and decide what the right pool size depends on.
- Write a migration that adds a `NOT NULL` column without a default to a table that has rows. Watch it fail. Keep the note for Phase 14.

## Definition of done

- [ ] `docker compose up` starts the API, and you can register, log in, create a project and a conversation through the OpenAPI UI.
- [ ] Integration and migration tests pass locally and in CI.
- [ ] A cross-tenant access test exists for every project-scoped endpoint.
- [ ] The image runs as a non-root user.
- [ ] Logs are JSON and carry a request ID end to end.

## Be able to explain

- What is the difference between liveness and readiness, and what breaks if the liveness probe checks the database?
- What happens when you call a blocking library inside an `async def` endpoint?
- Why should you read an autogenerated Alembic migration before applying it? Give two things autogenerate gets wrong.
- Where is tenant isolation enforced in your code, and how do you know no endpoint bypasses it?
- Which data went to MongoDB and which to Postgres, and what was the deciding property?
